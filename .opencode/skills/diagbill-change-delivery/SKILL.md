# OmniMed Core end-to-end change delivery

This skill is the default delivery workflow for **every change request** in this repository. Do not stop
at a local code edit when the user asked for a change. Treat "done" as: implemented, tested, documented,
committed, pushed, merged through a pull request, released, and the release verified on GitHub.

Load the relevant domain skill as well (`diagbill-billing`, `diagbill-licensing`,
`diagbill-security-offline`, `diagbill-sync`, `diagbill-hospital-pharmacy`, etc.). This skill governs
delivery; domain skills govern the actual behaviour.

## Non-negotiable rules

- Never push directly to `main`. The repository rule requires a pull request.
- Never commit `.env`, credentials, databases, `license-portal/keys/`, `license-portal/data/`, signing
  PFX files or passwords.
- Do not publish a release whose installers were not built from the merged release commit.
- Do not describe a release as signed unless `Get-AuthenticodeSignature` returns `Valid` for the app,
  NSIS installer and MSI installer.
- If a required step is genuinely blocked (signing certificate, GitHub permissions, failed test), stop and
  report the blocker; do not silently publish a partial release.
- Process-only changes (for example `.opencode/skills/` or internal contributor notes) may be merged
  without a new binary release unless the user explicitly asks for a release. Product code, schema,
  licensing, security, installer or user-facing documentation changes require a release.

## 1. Start clean and understand the change

```powershell
git status --short
git branch --show-current
git log -5 --oneline --decorate
gh release view --json tagName,publishedAt 2>$null
```

- Read the relevant source, tests, docs, skills and release workflow before editing.
- Identify whether the change affects schema, licensing, security, billing, data migration, installer
  behaviour, browser monitor behaviour or only documentation.
- Search for stale documentation claims rather than updating only one obvious file.

## 2. Implement and test

- Keep changes consistent with existing patterns and tenant isolation.
- Add or update automated tests where the risk warrants it.
- Run the full local gate:

```powershell
npm run check
npm run build
npm run build:monitor
cargo test --lib
```

- Add targeted manual checks for the affected workflow. For licensing changes, include hardware mismatch,
  DPAPI copy/tamper failure, clock rollback and legacy migration checks.
- Fix failures before proceeding. A red gate blocks the release.

## 3. Documentation sweep

Update every affected document, not just the changelog. Check:

- `README.md` and `CHANGELOG.md`
- `docs/*.md` relevant to the feature
- `CLIENT_INSTALLATION_RUNBOOK.md`, `BACKUP_RESTORE.md`, `DESKTOP_BUILD.md`,
  `PRODUCTION_COMMERCIAL_READINESS.md`, `PRE_RELEASE_CHECKLIST.md`, `SECURITY.md`
- `license-portal/README.md` and portal UI when licensing changes
- The relevant `.opencode/skills/*/SKILL.md`
- If tests, parameters, packages or catalogue counts change, regenerate
  `.opencode/skills/diagbill-test-catalogue/references/test-catalogue.md` and
  `.opencode/skills/diagbill-test-catalogue/references/packages.md` using
  `diagbill-test-catalogue/references/regenerate.md`
- Release notes and migration guidance

Useful stale-claim scan (avoid `target/` and `node_modules/`):

```powershell
Get-ChildItem src,src-tauri\src,docs,license-portal -Recurse -File -Include *.ts,*.tsx,*.rs,*.md,*.mjs,*.html |
  Where-Object { $_.FullName -notmatch '\\target\\|node_modules' } |
  Select-String -Pattern 'localStorage|OS-secure|device ID|clock rollback|tamper-proof'
```

## 4. Versioning

Use semantic versioning:

- patch: fixes, security hardening without new product capability
- minor: new capability
- major: incompatible product/data/API change

Update all version locations together:

- `package.json`
- `package-lock.json` (top-level and `packages[""].version`)
- `src-tauri/Cargo.toml`
- `src-tauri/Cargo.lock` (regenerated by `cargo check`)
- `src-tauri/tauri.conf.json`
- `CHANGELOG.md` (move the section from Unreleased to the release version and date)
- Release notes with a prominent upgrade/migration section when needed

Run `cargo check` after editing `Cargo.toml` so `Cargo.lock` updates.

## 5. Build and sign Windows installers

Build from the merged `main` commit, not from an uncommitted tree.

```powershell
git switch main
git pull --ff-only origin main
npm run check
npx tauri build
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\sign-windows.ps1
```

The signing script signs `src-tauri\target\release\medicore.exe`, regenerates bundles with
`--no-binary-patching`, signs the NSIS installer and MSI, and verifies all three signatures.

Expected certificate thumbprint:

```text
1180CA1A9509C9E968DED5E4274C89410AC52584
```

If the certificate is missing or signing fails, stop. Do not publish unsigned installers under a release
that claims to be signed.

## 6. Verify release artifacts

- Check the embedded executable inside the MSI, not only the installer shell:

```powershell
$target = Join-Path $env:TEMP 'medicore-msi-verify'
msiexec /a .\src-tauri\target\release\bundle\msi\OmniMed Core_X.Y.Z_x64_en-US.msi /qn TARGETDIR=$target
Get-AuthenticodeSignature "$target\PFiles\OmniMed Core\medicore.exe"
```

- Verify NSIS and MSI:

```powershell
Get-AuthenticodeSignature .\src-tauri\target\release\bundle\nsis\OmniMed Core_X.Y.Z_x64-setup.exe
Get-AuthenticodeSignature .\src-tauri\target\release\bundle\msi\OmniMed Core_X.Y.Z_x64_en-US.msi
```

- Confirm `ProductVersion` matches the release version.
- Perform an install/upgrade smoke test on a test profile or clean Windows environment. Confirm the app
  launches, the database opens, data survives the upgrade and the licensed modules are correct.
- Copy release assets into `release/vX.Y.Z/`:

```powershell
# NSIS, MSI, MediCore-CodeSigning.cer, SHA256SUMS.txt
Get-FileHash .\release\vX.Y.Z\* -Algorithm SHA256
```

Write `SHA256SUMS.txt` with lowercase SHA-256 values and exact filenames.

## 7. Commit, PR and merge

```powershell
git switch -c feat/<short-slug>
git add -A
git status --short
git commit -m "<type>(<scope>): <summary>"
git push -u origin feat/<short-slug>
gh pr create --base main --head feat/<short-slug> --title "<title>" --body "<summary and verification>"
gh pr checks <number> --watch
gh pr merge <number> --merge --delete-branch
```

- Wait for CI checks to pass before merging.
- Do not use admin bypass unless the user explicitly authorizes it.
- After merge:

```powershell
git switch main
git pull --ff-only origin main
git status -sb
```

## 8. Tag and publish the release

Confirm the version in `package.json` and `src-tauri/tauri.conf.json` matches the tag.

Because the current GitHub Actions release workflow builds **unsigned** installers, temporarily disable it
when publishing a locally signed release:

```powershell
gh workflow list --all
gh workflow disable "Release Windows"
git tag -a vX.Y.Z -m "OmniMed Core vX.Y.Z"
git push origin vX.Y.Z
```

Create the GitHub release with signed assets and the release notes file:

```powershell
gh release create vX.Y.Z --title "OmniMed Core vX.Y.Z" --notes-file <release-notes.md> --latest `
  .\release\vX.Y.Z\OmniMed Core_X.Y.Z_x64-setup.exe `
  .\release\vX.Y.Z\OmniMed Core_X.Y.Z_x64_en-US.msi `
  .\release\vX.Y.Z\MediCore-CodeSigning.cer `
  .\release\vX.Y.Z\SHA256SUMS.txt
```

Re-enable the workflow immediately, including on failure:

```powershell
gh workflow enable "Release Windows"
gh workflow list --all
```

If the workflow changes to signed CI builds later, remove the disable/enable step only after verifying
that CI produces signed assets with the correct certificate.

## 9. Verify the published release

```powershell
gh release view vX.Y.Z --json tagName,name,isDraft,isPrerelease,publishedAt,url,assets
gh release download vX.Y.Z --pattern SHA256SUMS.txt --dir <temp> --clobber
```

- Confirm the release is public, not a draft, and marked latest.
- Confirm asset names and sizes.
- Compare GitHub asset digests with local `SHA256SUMS.txt`.
- Confirm the release body contains the migration/upgrade warning and signing/root-cert instructions.

## 10. Final response format

Always report:

- PR URL and merge commit
- Tag and GitHub release URL
- Version and schema version
- Checks run and their results
- Assets and SHA-256 values
- Any migration steps the user/customer must take
- Any remaining limitation or unverified environment

## Definition of done

- [ ] Change implemented and tested
- [ ] Relevant domain skill loaded and followed
- [ ] All affected docs, runbooks, skills, portal docs and changelog updated
- [ ] Version bumped everywhere
- [ ] `npm run check`, terminal build, monitor build and Rust tests pass
- [ ] Merge commit is on `main`
- [ ] Tag points to the merged release commit
- [ ] Signed NSIS and MSI installers verified
- [ ] Embedded executable inside the MSI verified
- [ ] `SHA256SUMS.txt` and root certificate attached
- [ ] GitHub release published and marked latest
- [ ] Remote asset digests match local checksums
- [ ] Upgrade/migration warning included in release notes
- [ ] Final response contains links and migration instructions
